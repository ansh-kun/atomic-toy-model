1. Model description, assumptions, governing equations

A 2D toy particle system: N particles in a square box of side L, connected to every other particle within a cutoff radius rc by a Hookean (spring-like) pair force, and bouncing elastically off the box walls.

  • Pair force: Fij = -k (rij - r0), directed along the line joining particles i and j, applied only when rij < rc and i ≠ j.
  • Potential energy: Uij = 0.5 k (rij - r0)2
  • Kinetic energy: K = 0.5 Σ m v2
  • Wall handling: elastic reflection — the velocity component normal to a wall flips sign, position is clamped inside [0, L].
  • Integration: velocity-Verlet (half-kick, drift, recompute force, half-kick), unless otherwise noted (Task 3 also tests plain Euler for comparison).
  • Assumptions: all particles have equal mass (m=1); the pair interaction is the only internal force; the box walls are the only external influence.

Baseline parameters used throughout unless a task is explicitly varying one of them: N=16, L=10.0, rc=3.0, k=1.5, r0=2.5, dt=0.005, mass=1.0.

5. Task 4 — Dissipation and relaxation

Drag force F = -γv added to the spring force. Relaxation criterion: average particle speed must stay below 0.01 for the rest of the run, not just momentarily.

gamma     Relaxed by t=20?      decay tau   E_final   
------------------------------------------------------
0.0       No (conservative)     ~269        15.69     
0.05      No                    ~14.5       4.90      
0.1       No                    ~8.35       1.81      
0.5       Yes, at t=19.02       ~2.08       ~0.00

Answer: relaxation time decreases monotonically as γ increases (τ drops from ~269 to ~2 across the tested range) — more drag relaxes the system strictly faster, and only strong enough damping (γ=0.5 here) fully stops the system within an accessible simulation time.

6. Task 5 — Numerical precision: float32 vs float64

dtype     memory        median time   max drift   
--------------------------------------------------
float32   256 bytes     17.35 ms      5.43%       
float64   512 bytes     16.84 ms      5.43%

Memory ratio float64/float32 = 2.00× exactly, as expected. Final-position relative difference eps_pos = 6.6e-7 — negligible. At this small N (16), float32 showed no speed advantage (0.97×) because Python/NumPy call overhead dominates, not raw arithmetic — the speed benefit of float32 only shows up at the larger N tested in Task 6/7, where memory bandwidth is the bottleneck.

Answer: yes, float32 is accurate enough for this problem; its computational advantage is purely in memory footprint at this scale, and would extend to speed at larger N.

7. Task 6 — Computational efficiency and scaling

N       loop(s)   numpy(s)  C(s)      numpy x   C x       
----------------------------------------------------------
50      0.00139   0.00011   0.00001   12.4x     134.9x    
200     0.01169   0.00073   0.00004   13.6x     311.8x    
500     0.06586   0.00447   0.00016   14.2x     425.8x    
1000    0.26955   0.01873   0.00054   14.2x     484.8x

All three methods were checked to produce matching forces (within 1e-6) at every N before any timing was trusted.

Bottleneck: the Python loop is limited by per-iteration interpreter overhead, not the arithmetic. NumPy removes that overhead but still allocates full (N,N,2)-shaped temporaries even for pairs outside the cutoff, so it does genuine O(N²) work and memory traffic. The C version has neither problem and is limited only by raw floating-point throughput — speedup over the Python loop grows with N (135x to 485x) because the fixed per-call overhead matters less as the real workload grows.

At N=10000 the theoretical (N,N,2) array alone needs 1.6 GB for float64, and compute_forces builds roughly five more same-sized temporaries simultaneously (distance matrix, mask, safe-distance, direction, magnitude) — multiple GB at once just for one force evaluation. We did not allocate it on this machine for that reason.

Answer: the fully vectorized approach becomes impractical somewhere around N=5,000–10,000 on a typical laptop — not because any single array is impossible to allocate, but because several same-sized temporaries exist at once and memory grows as N², so doubling N quadruples the memory (confirmed exactly by the table above).

9. Task 8 — Innovation: a cell-linked neighbor list

Instead of comparing every particle to every other particle, particles are binned into a grid of cells the size of the cutoff radius; each particle only needs to check the 9 cells around it. For a fixed particle density this turns an O(N²) calculation into an O(N) one.

N       cell list(s)  brute force(s)                speedup   
--------------------------------------------------------------
500     0.0025        0.0047                        1.9x      
1000    0.0049        0.0183                        3.7x      
2000    0.0099        0.0753                        7.6x      
5000    0.0251        0.5443                        21.7x     
10000   0.0536        skipped (Task 7: unsafe mem)  -

Correctness first: at N=200, the cell list's forces matched the brute-force result to within 1.8e-15 (floating-point noise) — it is exact, not an approximation.

What it improved and the evidence: speedup grows with N (1.9x to 21.7x across the range actually compared), consistent with O(N) vs O(N²) scaling, and the cell list keeps running (0.054s at N=10,000) exactly where Task 7 showed the brute-force array becomes impractical to even allocate. This directly fixes the scalability limit identified earlier in the project.

10. Task 9 — Final computational engineering recommendation

Choice          Recommendation                                  
----------------------------------------------------------------
Precision       float64 generally; float32 if memory-constrained
Timestep        dt = 0.01                                       
Integrator      velocity-Verlet                                 
Force calc      NumPy for small N; cell list beyond ~1000       
Cutoff radius   rc = 3.0 (unchanged)                            
Dissipation     gamma = 0.1                                     
Innovation      cell-linked neighbor list

One-paragraph summary. For a system this size (tens to low hundreds of particles), float64 with dt=0.01, velocity-Verlet, and the plain NumPy vectorized force calculation is the simplest correct and fast-enough choice. The moment N climbs into the thousands, two things from Task 7 become real problems — the O(N²) memory for the pairwise array and the O(N²) time — and the cell-linked list from Task 8 is what actually fixes both, at no cost in accuracy. That is the central engineering lesson of this project: a method that looks fine at N=16 is not automatically the right method at N=10,000, and you only find out which one to use by actually measuring, not by guessing.

11. Limitations

  • 2D only; all particles share one mass; only a single Hookean interaction type was tested.
  • The relaxation criterion (average speed < 0.01, sustained) is one reasonable choice among several defensible ones — low-γ systems genuinely may never relax under elastic wall collisions, which is itself a finding, not a bug.
  • The cell list's correctness relies on cell size ≥ cutoff radius; it was only verified at N=200 directly, though it is checked to reproduce the exact brute-force result there.
  • Timing numbers are specific to this machine (Apple Silicon, clang -O2); absolute numbers will differ elsewhere, though the relative orderings should not.
